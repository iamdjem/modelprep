# Platform integration audit, 2026-08-07

Nine platforms audited for the defect classes found in Thangs: wrong field names, wrong content formats, unimplemented platform features, and stale capture-doc claims. 105 raw findings.

Tags: **[C] CONFIRMED** = quoted from our code or a capture doc. **[S] SUSPECTED** = the code fact is proven, the platform consequence is inference. Do not report [S] items as known bugs.

Spot-verified by hand after the audit: X1 (all four `mdToHtml` defects reproduced by executing the function), X2 (Nexprint check at App.jsx:2673 reads `project.files` while videos live in `project.media`), X4 (MMF `maxImages: null` meets `platform.maxImages || 20`, silently dropping images 21+).

## Part 1: cross-cutting defects (fix these first, one change fixes many platforms)

### X1. One incomplete Markdown converter feeds four platforms [C]
`mdToHtml` (`deploy/src/lib/format.js:15-37`) understands only `#{1,3}` headings, `-`/`*` bullets, fenced code, and inline bold/italic/link/code. Every other line falls through to `paraBuf.push(line)` (`format.js:33`) and paragraph lines are joined with a space (`format.js:19`).

Consequences, all confirmed by executing the function or by reading its branches:
- Ordered lists collapse: `1. First\n2. Second` becomes `<p>1. First 2. Second</p>`, i.e. two assembly steps become one run-on sentence.
- Blockquotes leak: `> Note:` becomes `<p>&gt; Note:</p>`.
- `![alt](url)` becomes `!<a href="url">alt</a>` because the link rule at `format.js:11` matches inside the image syntax and orphans the bang.
- `~~strike~~` leaks literally (no rule in `inlineFormat`, `format.js:8-13`).
- `#### x` produces nothing usable for platforms whose editors go to h6, while `mdToHtml` also emits `<h1>`/`<pre>` for platforms whose toolbars do not have them.

Callers and the capability each platform documents as supported:
- Printables `deploy/src/App.jsx:9224` (doc records ordered lists, blockquote, strikethrough as live editor capabilities).
- MyMiniFactory `deploy/src/App.jsx:10619` (doc records a numbered-list toolbar button).
- MakerOnline `deploy/src/App.jsx:10402` (doc records a Quill toolbar with h1-h6, blockquote, ordered lists).
- MakerRoad `deploy/src/App.jsx:10213` (`descFormat: 'html'` is internally consistent, but `<h1>` is the same risk MakerWorld documents for CKEditor).

**Smallest fix:** port the ordered-list (`^\s*\d+\.\s+`) and blockquote (`^>\s?`) branches that already exist in the sibling `mdToMakerWorldHtml` (`format.js:50-79`) into `mdToHtml`, anchor the link rule with `(?<!!)` (or handle `!` first), and add a `~~` rule to `inlineFormat`. Heading depth should become a per-platform ceiling rather than a hardcoded `Math.min(h+1, 6)`.

Related, same file: `mdToMakerWorldHtml` violates its own header comment by emitting `<h5>/<h6>` (`format.js:60-61`) when the documented MakerWorld schema is h2-h4. Clamp to 4. [C]

### X2. Video warnings read the wrong array, so they can never fire [C]
Videos are written to `project.media` (`App.jsx:4811`), never to `project.files` (the model-file drop handler at `App.jsx:2822-2834` does not accept mp4/webm at all).

- Nexprint check: `App.jsx:2673` inspects `project.files`. Dead. Also omits `.mov`, which the file input accepts and the doc names.
- Creality check: `App.jsx:2693`. Same dead check, same copy origin.
- MakerRoad does it right at `App.jsx:2745-2752` by reading `project.media`. Copy that predicate into both.
- Thingiverse (`App.jsx:2793-2800`) and MakerOnline (`App.jsx:2703-2744`) have no video check at all, and their upload filters skip video extensions silently.

**Smallest fix:** one shared `projectHasVideo(project)` helper reading `project.media`, called from all five preflight blocks.

### X3. `withoutExcluded()` is skipped on secondary file classes [C]
The per-platform file picker only lists files matching `platform.formats` (`App.jsx:498-503`), and two flows upload a second file class without honouring exclusions:
- Nexprint attachments: `App.jsx:9589-9590` is a bare `project.files.filter(...)` while the line immediately above (`:9587`) wraps model files in `withoutExcluded`. A Creality instruction PDF in the project is pushed onto the Nexprint listing with no UI to stop it.
- MakerOnline documentation: `App.jsx:10331`, the only publish filter with no `withoutExcluded`.

Creality (`:9918`), MakerOnline models (`:10336`) and MakerRoad (`:10187`) all wrap correctly. **Fix:** add the wrap in both places, and add attachment/documentation formats to `platformCandidateFiles` so the user can see and untick them.

### X4. Invented caps presented to the user as platform requirements [C]
`platform-specs.md:56-59` and `App.jsx:491-494` both state the house rule (do not reintroduce unverified caps). These violate it:

| Where | Value | Reality |
|---|---|---|
| `App.jsx:10598` | `platform.maxImages \|\| 20` for MMF | MMF entry sets `maxImages: null` with a comment forbidding a gallery limit; doc says UNKNOWN. Images 21+ vanish with no warning because the warning at `App.jsx:2614` is gated on `platform.maxImages` being truthy. |
| `App.jsx:457` | Creality `maxFileMb: 2048` | No Creality doc records any model-file cap. Produces a hard blocking error. |
| `printables-model.js:6-7` | price 5-150 | Doc says bounds are server-provided; live probe ruled out `minPrice`/`maxPrice`/etc., so the source is unlocated. |
| `makerworld-validation.ts:85`, `makerworld.js:208` | 200MB raw laser file | Doc explicitly says UNKNOWN and "do not infer". |
| `makerworld-validation.ts:40`/`:88`, `App.jsx:386` | 250MB aggregate | Appears in no live doc, only in our own flow map. |
| `App.jsx:412` | MMF cover 1920x1440 4:3 | No capture evidence for any MMF ratio. |
| `App.jsx:463-470` | MakerOnline 1600x1200 4:3 | Doc explicitly says no required crop. |

**Fix pattern:** unset the value, and make the warning path fire on the absence of a cap rather than silently applying a default. For MMF specifically change `platform.maxImages || 20` to `platform.maxImages ?? Infinity` (or drop the slice), which is a one-token change that stops the silent drop.

### X5. Documented caps that we do not enforce, so failure happens after the bytes are uploaded [C]
The mirror image of X4:
- Cults `flat_keywords`: 20 tags / 300 chars documented, the Cults `PLATFORMS` entry (`App.jsx:400-409`) has no `limits` object at all, so `App.jsx:2619-2620` never runs.
- Cults price: documented min 0.65 / max 1200 / step 0.01, only check is a warning at `App.jsx:2625`.
- Cults 8000x8000 image cap: never checked, although `naturalW`/`naturalH` are already stored (`App.jsx:4851-4852`) so the doc's stated reason for not checking is obsolete.
- MakerRoad 500MB model total / 50MB doc total: `App.jsx:477` sets `maxTotalMb: null` and the UI prints "Total cap: No limit listed". The real check lives in `makeroad-direct.js:107-108` inside `buildSubmitPayload`, i.e. after `uploadMany` already pushed every byte.
- MakerWorld `.3mf` is capped at 150MB in four places (`makerworld-validation.ts:38`, `makerworld-direct-entry.ts:172` and `:184`, `makerworld.js:208`, warning text `App.jsx:3673`) when the current live spec is 200 MiB; a legitimate 150-200 MiB Bambu file is rejected and never reaches the platform. Conversely `.lac` is allowed 200MB against a documented 100 MiB cap.
- MakerOnline `print_desc`: 1000-char doc cap, the typed field is capped at `App.jsx:6963` but the `project.profiles[0].description` fallback at `App.jsx:10422` is uncapped and then has HTML added on top.
- MMF 5 MiB image cap: only enforced in `myminifactory-direct.js:307`, after several images have transferred.

**Fix:** move every documented cap into the platform `limits` object and check it in `platformPreflight` before any upload starts.

### X6. Read-back verification cannot see the fields most likely to be wrong [C]
Every format defect above survives our "verified" reporting because the verifier does not compare the affected field:
- MMF `parseEditPage` (`myminifactory-direct.js:163-267`) returns no description and no tags, although the doc records both as readable (`threedObjectTags` on edit).
- MakerRoad `makerRoadReadbackIssues` (`App.jsx:6686-6707`) compares title, `visible`, `plan`, `payType` and role counts only, never `descBody`, `printType`, `descColumn`, or any publication/review state.
- Printables summary: `printablesReadbackMismatches` (`printables-model.js:185`) compares the mangled value against itself, so the summary-stripping bug in P4 below verifies clean.

**Fix:** add description and tags to the MMF readback parser, and add `descBody`/`printType`/state to the MakerRoad comparison. This is the cheapest way to stop shipping "saved and verified" over wrong content.

### X7. Declarations the user never made, sent on every upload [C]
Same family as the Thangs `isAiGenerated` bug:
- MakerWorld `isAIGC: false` hardcoded in both builders (`makerworld-web.ts:600`, `:911`), no UI anywhere, no doc record of the control. The same App exposes an AI disclosure for Printables, Thingiverse and MakerOnline.
- MakerWorld `nsfw`: plumbed end to end (`makerworld-web.ts:520`, `:908`) but `MW_DEFAULT_OPTS` (`App.jsx:911-918`) has no key and `MakerWorldOptions` renders no control, so a mature model is always declared safe. Every other platform card exposes it.
- MMF: `no_derivatives`/`non_commercial`/`exclusive` are always submitted as computed 0/1 (`myminifactory-direct.js:470-472`) where the native form submits them empty; `license_id` is authoritative today. [S] on server behaviour.
- Thingiverse `included_apps: [1127]` on every Thing (`thingiverse-direct.js:5`, `:59`), value recorded nowhere. [S] that it is Customizer.
